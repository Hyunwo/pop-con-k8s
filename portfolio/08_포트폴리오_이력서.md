# 08. 포트폴리오 / 이력서 정리

## 프로젝트 한 줄 요약
팝업스토어 이벤트 오픈 순간 22,500명 동시 접속을 목표로 한 MSA 기반 티켓팅 서비스의
클라우드 인프라 설계 및 구축 (KDT DevOps 팀 프로젝트, 2026.03 ~ 2026.04)

## 담당 역할 (본인이 직접 한 것)
- **Istio 서비스 메시 설계 및 구축** (메인 담당)
  - VirtualService, DestinationRule, PeerAuthentication, AuthorizationPolicy 작성
  - mTLS STRICT 모드 적용으로 내부 통신 전 구간 암호화
  - 서비스별 Circuit Breaker 차등 설계
- **EKS 클러스터 운영**
  - Karpenter NodePool 관리 (Spot 좀비 NodeClaim 문제 해결)
  - 노드 상태 모니터링 및 정리
- **GitOps 배포 관리**
  - gitops 레포 매니페스트 작성 및 관리
  - ArgoCD를 통한 서비스 배포
- **트러블슈팅**
  - startupProbe 타임아웃 문제 진단 및 해결 (auction, draw, user)
  - Istio AuthorizationPolicy SA 이름 불일치 해결
  - Envoy 사이드카 OOMKilled 해결

## 주요 성과 (수치 포함)

### 안정성
- Karpenter Spot 좀비 NodeClaim 근본 해결
  - terminationGracePeriod 설정 + Spot 풀 고갈 인스턴스 타입 제거
- startupProbe 타임아웃 문제 해결
  - 로그 분석으로 앱 기동 시간(184초) > probe 허용 시간(180초) 불일치 파악
  - failureThreshold 15→30으로 수정

### 서비스 메시 (Istio)
- mTLS STRICT 모드로 내부 통신 전 구간 암호화 (Zero Trust 네트워크)
- 서비스별 Circuit Breaker 차등 설계
  - 경매/드로우: 3회 연속 실패 시 차단 (정합성 중요)
  - 일반 서비스: 5회
- AuthorizationPolicy로 서비스 간 접근 제어
- Envoy 사이드카로 코드 수정 없이 메트릭/트레이스 자동 수집

### 부하테스트
- Scenario 1: 350만 건 처리, 성공률 99.15%, median 41ms
- Scenario 2: 경매 bid 100% 성공, **초과 판매 0건** (Redis 원자적 연산)
- Scenario 3: draw_entry 100%, **중복 응모 0건**, VU 2.5배 증가에도 안정

## 이력서 문구 예시

### 방식 1 (간결)
- AWS EKS 기반 MSA 서비스 인프라 설계 및 구축
- Istio 서비스 메시 도입으로 mTLS 기반 내부 통신 보안 및 Circuit Breaker 구현
- Karpenter를 활용한 Spot 인스턴스 자동 프로비저닝으로 비용 최적화
- ArgoCD GitOps로 8개 마이크로서비스 배포 자동화
- k6 부하테스트로 22,500명 동시 접속 시나리오 검증 및 병목 분석

### 방식 2 (성과 중심)
- Istio mTLS STRICT 모드 적용으로 클러스터 내부 통신 전 구간 암호화 (Zero Trust)
- Karpenter Spot 인스턴스 좀비 NodeClaim 문제 로그 분석으로 근본 원인 파악 및 해결
- 부하테스트(k6) 3개 시나리오 설계 및 진행, 초과 판매 0건/중복 응모 0건 정합성 검증
- startupProbe 타임아웃 문제를 로그 분석으로 진단하고 failureThreshold 조정으로 해결

## 회고

### 잘 한 것
- 설계 단계에서 트래픽 패턴을 미리 분석하고 서비스별로 분리한 것
- 코드 수정 없이 인프라 레벨에서 보안, 모니터링, 확장을 해결한 것
- 부하테스트로 실제 한계를 수치로 확인하고 솔직하게 드러낸 것

### 아쉬웠던 것
- startupProbe 같은 공통 설정이 서비스마다 통일되지 않아 같은 문제가 반복됨
- 목표 CCU 22,500명을 실제 테스트에서 완전히 검증하지 못함
- Queue 병목을 발견했지만 개선까지는 시간이 부족했음

### 다음에 다르게 할 것
- 공통 설정은 처음부터 표준화해서 반복 실수 제거
- 부하테스트를 배포 파이프라인에 포함시켜 조기 문제 발견
- KEDA로 Queue 길이 기반 스케일링 도입
- Redis 고가용성 구성 (Cluster 또는 Sentinel)

## 추가 기술 상세

### ServiceEntry 관리
- Istio mTLS STRICT 환경에서 외부 서비스(RDS, Redis, 카카오/네이버 OAuth, 포트원 결제, VQA) 접근을 명시적으로 허용
- ServiceEntry 미등록 시 Envoy가 외부 요청 차단 → 소셜 로그인, 결제 기능 불가

### HPA 스케일링 정책 세부 설정
- scaleUp stabilizationWindowSeconds: 0 → 트래픽 급증 시 즉시 반응
- scaleDown stabilizationWindowSeconds: 300 → 급격한 스케일다운 방지
- minReplicas: 2, maxReplicas: 10

### PDB (Pod Disruption Budget)
- minAvailable: 1로 설정
- 노드 드레인, 롤링 업데이트 중에도 최소 1개 Pod 유지

### Lambda 비용 최적화
- Bastion 서버 EC2를 Lambda + EventBridge로 업무 시간 외 자동 중지
- 비용 절감 목적

### 소셜 로그인 / 결제 연동
- 카카오, 네이버 소셜 로그인
- 포트원(PortOne) 결제 API 연동

### VQA (보안 퀴즈)
- 매크로 방지를 위한 외부 VQA 서버 연동
- 경매/드로우 진입 전 퀴즈 통과 필요
- 부하테스트에서 VQA가 주요 병목으로 확인됨

### anti-macro S3
- 매크로 탐지 시그널 데이터를 S3에 저장
- terraform에서 popcon-anti-macro-signals 버킷 + IAM Policy 구성
