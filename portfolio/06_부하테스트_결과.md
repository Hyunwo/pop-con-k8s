## Scenario 1: 이벤트 전 탐색 부하

### 설계
- 대상: 홈/카테고리/추천 API
- 설계 목표: 22,500 VU, 10분 점진 투입
- 실제 테스트: 최대 5,000 VU
- 목표 RPS: 2,250

### 결과
| 항목 | 수치 |
|---|---|
| 총 요청 수 | 3,500,228건 |
| 최대 VU | 5,000 |
| 성공 요청 | 3,470,557건 (99.15%) |
| 실패 요청 | 29,671건 (0.85%) |
| min | 32ms |
| median | 41ms |
| avg | 122ms |
| P90 | 190ms |
| P95 | ~300ms |
| max | 22.7초 |

### 분석
- median 41ms: 대다수 요청은 빠르게 처리됨
- avg 122ms가 median보다 3배 높음: 느린 요청들이 평균을 끌어올림
- max 22.7초: 피크 구간에서 일부 요청 극단적 지연 (꼬리 지연)
- **SLO 달성**: 에러율 0.85% (1% 미만 목표 달성)

## Scenario 2: 경매 오픈 스파이크

### 설계
- 5,000 VU → 50 VU 구간 탐색 (총 9회 실행)
- SSE 연결 + 경매 플로우 병렬 → 통과율 낮아 SSE 제외
- 최종: 경매 진행 플로우만으로 검증
- SSE 자체는 별도 검증에서 500 VU 8,379건 전부 통과 (안정적)

### 결과
**안정 구간: 50~75 VU**
| 단계 | 결과 |
|---|---|
| page_entry | 75/75 (100%) |
| anti_macro | 75/75 (100%) |
| vqa_post (퀴즈 통과) | 60/75 (80%) |
| bid_200 | 60/60 (100%) |
| queue_enter | 75/75 (100%) |
| vqa_get | 75/75 (100%) |
| auction_detail | 60/60 (100%) |
| reservation | 60/60 (100%) |

**병목 분석**
| 구간 | 현상 |
|---|---|
| Queue | VU 증가에 따라 처리율 급감 (200 VU 이상: 10~18%대) |
| VQA | 100 VU 재시도 시 vqa_get 49% 실패, 서비스 응답 불가 |
| SSE | 별도 검증에서 안정적 (경매 플로우와 독립적 동작) |

### 핵심 성과
- bid 로직 end-to-end 100% 성공
- **초과 판매 0건** (Redis 원자적 연산으로 정합성 보장)
- 병목은 bid 로직이 아닌 앞단 진입 제어 계층 (Queue, VQA)

## Scenario 3: 드로우 대기열 집중

### 설계
- 설계 목표: 1분 내 22,500명 대기열 진입 → 15분 폴링 Steady
- 실제 테스트: 200 VU → 500 VU (2회)
- 지속 구간 최대 RPS: 7,500 (세 시나리오 중 가장 높은 지속 부하)

### 결과
| 항목 | 수치 |
|---|---|
| check 통과율 | 94.9~95.7% |
| draw_entry 성공률 | 100% (중복 방지 검증 포함) |
| queue 처리율 | 55~60% (VU 증가에도 안정적 유지) |

**500 VU 플로우 단계별 통과율**
| 단계 | 결과 |
|---|---|
| page_entry (draw_detail) | 500/500 (100%) |
| anti_macro_1 | 500/500 (100%) |
| vqa (퀴즈 통과) | 301/301 (100%) |
| anti_macro_2 | 301/301 (100%) |
| user_id | 500/500 (100%) |
| queue_enter | 301/500 (60%) |
| draw_dates/draw_options | 301/301 (100%) |
| draw_entry + 중복방지 | 301/301 (100%) |

### 경매 시나리오와 차이점
- VQA: 경매에서 49% 실패했던 vqa_post 실패 없음 → 드로우 서비스 처리 용량 더 큼
- VU 2.5배 증가해도 지표 변동 거의 없음 (안정적 확장)
- **중복 응모 0건**
