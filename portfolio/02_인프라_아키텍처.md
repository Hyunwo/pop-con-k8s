# 02. 인프라 아키텍처

## 외부 아키텍처 (요청 흐름)
```
사용자 → Cloudflare → ALB → Istio Ingress Gateway → EKS 각 서비스
                                                    → RDS (Private Subnet)
                                                    → Redis (Private Subnet)
```

## Cloudflare
- 역할: DNS 위임을 통한 엣지 레벨 1차 방어선
- DDoS 방어: 레이어 3/4/7 공격 자동 탐지/차단, 오리진 서버 보호
- CDN 캐싱: 전 세계 300+ POP에서 정적 자원 캐싱, 응답 속도 향상
- DNS 관리: popcon.store, api.popcon.store
- 플랜: 무료 플랜 사용

## ALB (Application Load Balancer)
- 로드 분산
- Istio Ingress Gateway로 트래픽 전달

## Istio Ingress Gateway
- 외부 트래픽 진입 제어
- popcon.store → frontend 서비스
- api.popcon.store → 8개 백엔드 서비스

## EKS 클러스터
- 클러스터명: t1-prod-eks
- 리전: ap-northeast-2 (서울)
- 가용 영역: ap-northeast-2a, ap-northeast-2c
- 쿠버네티스 버전: 1.35
- 노드 운영체제: Amazon Linux 2023

## Karpenter (노드 자동화)
- NodePool명: t1-prod-eks
- 인스턴스 타입: t3a.large, t3a.xlarge, t3.large, t3.xlarge
  - medium 제거 이유: ap-northeast-2c Spot 풀 고갈로 좀비 NodeClaim 반복 발생
- capacity-type: spot + on-demand (Spot 우선)
- 가용 영역: ap-northeast-2a, ap-northeast-2c
- expireAfter: 720h (30일)
- terminationGracePeriod: 10m (좀비 NodeClaim 방지)
- consolidationPolicy: WhenEmptyOrUnderutilized
- consolidateAfter: 300s (5분 유휴 후 통합)
- limits: cpu 32, memory 128Gi
- Spot 중단 처리: SQS + EventBridge로 2분 전 신호 감지 → Pod 선제 이동

## HPA (수평 Pod 자동 확장)
- 기준: CPU 사용률 60%
- Pod request 200m 기준 → 실제 120m 초과 시 스케일아웃
- HPA → Pod Pending → Karpenter 노드 프로비저닝 연계

## 데이터 계층
### RDS MySQL
- Multi-AZ 구성
- RDS Proxy 앞단 배치: Pod 수 증가에 따른 DB 연결 폭발 방지
- Private Subnet 배치 (외부 직접 접근 차단)
- DB_HOST: RDS Proxy 엔드포인트

### Redis (ElastiCache)
- 역할: 인메모리 캐시 + 실시간 상태 처리 + 대기열 순번 관리
- Redisson 클라이언트 사용 (Spring Boot)
- Private Subnet 배치
- 단일 노드 운영 (향후 Cluster/Sentinel 구성 필요)

## 시크릿 관리
- AWS Parameter Store: DB 비밀번호, JWT Secret 등 민감 정보 중앙 관리
- External Secrets Operator: Parameter Store → K8s Secret 자동 주입
- IRSA (IAM Roles for Service Accounts): 서비스별 AWS 권한 관리
  - backend-user: S3 접근 권한 (프로필 이미지 업로드)
  - 각 서비스 SA에 IAM Role ARN 어노테이션

## 모니터링 스택
- Prometheus: 메트릭 수집
- Grafana: 대시보드 시각화 (부하테스트 결과, 노드 현황, 응답시간)
- Jaeger: 분산 트레이싱
- Kiali: 서비스 메시 시각화 (트래픽 흐름, mTLS 상태)
- 수집 방법: Envoy 사이드카 자동 수집 (코드 수정 불필요)
- Pod 어노테이션: prometheus.io/scrape: "true"

## CI/CD 파이프라인
```
코드 Push → GitHub Actions (CI)
  → 빌드 + 테스트
  → Docker 이미지 빌드
  → ECR Push (이미지 태그: 커밋 SHA)
  → gitops 레포 이미지 태그 업데이트
  → ArgoCD 감지 → EKS 자동 배포 (CD)
```

- 배포 전략: Rolling Update (기본)
- revisionHistoryLimit: 2
- ArgoCD sync-wave 어노테이션으로 배포 순서 제어

## Terraform 구조
- S3 backend로 state 파일 관리
- 모듈 구성: eks, rds, redis, karpenter, iam, vpc 등
- global/iam: IAM 리소스 (IRSA용 Role, Policy)
- AWS 계정 전환 이력 있음 (프로젝트 중간 계정 변경)

## 인프라 설계 4대 원칙
1. 고가용성: Multi-AZ, Pod 분산, RDS Multi-AZ
2. 데이터 격리: Private Subnet, mTLS
3. 자동 확장: Karpenter + HPA
4. 엣지 방어: Cloudflare

## IRSA (IAM Roles for Service Accounts) 상세

### IRSA란
- Pod에 AWS 자격증명(Access Key)을 직접 넣지 않고
- ServiceAccount에 IAM Role을 연결해서 AWS 리소스에 접근하는 방식
- OIDC Provider를 통해 K8s SA → IAM Role Assume
- **최소 권한 원칙**: 서비스별로 필요한 권한만 부여

### 구성된 IRSA 목록

| 서비스 | IAM Role | 권한 |
|---|---|---|
| ALB Controller | t1-prod-eks-alb-controller-role | ALB 생성/수정/삭제 |
| External Secrets | t1-prod-eks-external-secrets-role | SSM Parameter Store 읽기 |
| EBS CSI Driver | t1-prod-eks-ebs-csi-role | EBS PV 프로비저닝 |
| Loki | t1-prod-eks-loki-role | S3 로그 저장 |
| **backend-user** | **t1-prod-eks-user-service-s3-role** | **S3 프로필 이미지 업로드/삭제** |

### backend-user S3 IRSA (직접 작업)

**목적**: 사용자 프로필 이미지를 S3에 업로드/삭제하기 위한 권한 부여

**Terraform (irsa.tf)**
```hcl
resource "aws_iam_role" "user_service_s3" {
  name = "${var.name}-user-service-s3-role"
  assume_role_policy = jsonencode({
    Statement = [{
      Action = "sts:AssumeRoleWithWebIdentity"
      Condition = {
        StringEquals = {
          "${oidc_issuer}:sub" = "system:serviceaccount:popcon-prod:backend-user"
          "${oidc_issuer}:aud" = "sts.amazonaws.com"
        }
      }
    }]
  })
}
```

S3 권한: `assets-popcon-store` 버킷의 `profiles/*` 경로에만 PutObject/DeleteObject/GetObject 허용

**K8s ServiceAccount (gitops)**
```yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: backend-user
  namespace: popcon-prod
  annotations:
    eks.amazonaws.com/role-arn: arn:aws:iam::529424689502:role/t1-prod-eks-user-service-s3-role
```

**동작 원리**
```
backend-user Pod 실행
  → SA의 role-arn 어노테이션 감지
  → EKS가 OIDC 토큰 자동 마운트
  → AWS STS에서 임시 자격증명 발급
  → S3 접근 가능 (Access Key 불필요)
```

### 면접 어필 포인트
- Access Key를 코드/환경변수에 넣지 않아 자격증명 유출 위험 제거
- 서비스별 최소 권한 원칙 적용 (user 서비스는 profiles/* 경로만 접근 가능)
- Terraform으로 IRSA 구성 자동화

## ServiceEntry (외부 서비스 접근 허용)

Istio mTLS STRICT 환경에서는 외부 서비스 접근도 명시적으로 허용해야 함.
등록된 외부 서비스 목록:

| ServiceEntry | 목적 | 포트 |
|---|---|---|
| rds-mysql | RDS MySQL 접근 | 3306 |
| elasticache-redis | Redis 접근 | 6379 |
| portone-api | 결제 API (포트원) | 443 |
| kakao-oauth | 카카오 소셜 로그인 | 443 |
| naver-oauth | 네이버 소셜 로그인 | 443 |
| vqa-server | VQA(보안퀴즈) 외부 서버 | 443 |

→ **소셜 로그인(카카오, 네이버), 결제(포트원), VQA** 모두 ServiceEntry로 등록

## HPA 상세 설정

```yaml
minReplicas: 2
maxReplicas: 10
averageUtilization: 60  # CPU 60% 기준

scaleUp:
  stabilizationWindowSeconds: 0   # 즉시 스케일아웃
  policies:
    - type: Percent, value: 100   # 현재 Pod 수의 100%씩 증가
    - type: Pods, value: 4        # 최대 4개씩 증가
  selectPolicy: Max               # 둘 중 더 큰 값 선택

scaleDown:
  stabilizationWindowSeconds: 300  # 5분 안정화 후 스케일다운
  policies:
    - type: Pods, value: 1        # 1개씩 감소
```

- scaleUp stabilizationWindowSeconds: 0 → 트래픽 급증 시 즉시 반응
- scaleDown stabilizationWindowSeconds: 300 → 급격한 스케일다운 방지

## PDB (Pod Disruption Budget)

```yaml
minAvailable: 1
```
- 노드 드레인, 업데이트 등 disruption 시 최소 1개 Pod 유지 보장
- 롤링 업데이트 중 서비스 중단 방지

## Lambda (EC2 스케줄러)

- 목적: Bastion 서버 등 EC2 인스턴스를 시간대별로 자동 시작/중지
- 구성: AWS Lambda + EventBridge (스케줄)
- 권한: EC2 StartInstances, StopInstances, DescribeInstances
- 비용 절감 목적 (업무 시간 외 자동 중지)

---

## Bastion 서버

- Private Subnet 내 RDS, Redis에 직접 접근하기 위한 점프 서버
- EKS 노드 보안 그룹, RDS 보안 그룹에 허용
- Lambda로 시간대별 자동 시작/중지 스케줄링
