# 04. 트러블슈팅 이력

## 1. 좀비 NodeClaim 문제 (Karpenter)

### 현상
- Spot 인스턴스 중단 시 NodeClaim이 삭제되지 않고 좀비 상태로 남음
- 수동으로 지워도 계속 재발
- 노드는 사라졌는데 NodeClaim이 남아 클러스터 상태 불일치

### 로그
```
karpenter: "attempted to remove nonexistent offering (t3a.medium, ap-northeast-2c, spot)"
```

### 원인
- ap-northeast-2c AZ의 t3a.medium, t3.medium Spot 풀 고갈
- Karpenter가 중단된 노드의 finalizer를 정상 처리 못하는 race condition

### 해결 과정
1. 수동 삭제 시도 → 재발
2. kubectl patch로 finalizer 강제 제거 → 임시 해결, 재발
3. Karpenter 로그 분석으로 근본 원인 파악 (medium Spot 풀 고갈)
4. **영구 해결**:
   - NodePool에서 t3a.medium, t3.medium 제거
   - terminationGracePeriod: 10m 추가 (10분 내 정리 안 되면 강제 종료)

### 파일
- gitops/prod/karpenter/nodepool.yaml

### 교훈
- 증상(좀비 노드)만 치료하지 말고 근본 원인(Spot 풀 고갈) 파악이 중요
- Karpenter 로그가 핵심 단서였음

## 2. startupProbe 타임아웃 (auction → draw → user 반복)

### 현상
- 새 이미지 배포 시 Pod 재시작 반복 (CrashLoopBackOff)
- startupProbe HTTP 500 오류 지속
- 기존 이미지는 정상 동작

### 로그 (결정적 단서)
```
19:56:42  Started DrawApplication in 172.608 seconds
19:56:43  draw-pool - Shutdown initiated...  ← 1초 뒤 강제 종료
```
앱이 정상 기동 완료했는데 바로 종료됨

### 원인
- startupProbe 최대 허용 시간 = initialDelaySeconds(30) + failureThreshold(15) × periodSeconds(10) = **180초**
- 실제 앱 기동 시간 = **~184초** (4초 초과)
- 앱이 184초에 기동 완료됐지만 이미 180초에 SIGTERM 발송된 상태

### 해결
- failureThreshold: 15 → **30** (최대 허용 시간 180초 → 330초)
- auction, draw, user 서비스 모두 동일하게 적용

### draw 서비스 추가 발견
- 이전 이미지에서는 JPA 쿼리 버그 별도 존재
- DrawEntryRepository.countOngoingByUserId()에서 존재하지 않는 `announcementAt` 필드 참조
- 에러: `UnknownPathException: Could not resolve attribute 'announcementAt' of Draw`
- Spring Boot 시작 시 모든 Repository 쿼리 검증 → 앱 자체가 뜨지 못함
- 개발팀 코드 수정 후 재배포로 해결

### 파일
- gitops/prod/backend/auction/deployment.yaml
- gitops/prod/backend/draw/deployment.yaml
- gitops/prod/backend/user/deployment.yaml

### 교훈
- 로그의 타임스탬프를 정확히 읽는 것이 핵심
- 같은 설정 문제가 서비스마다 반복됨 → 공통 설정 표준화 필요
- startupProbe 설정: initialDelaySeconds + failureThreshold × periodSeconds = 최대 허용 시간

## 3. Istio AuthorizationPolicy SA 이름 불일치

### 현상
- AuthorizationPolicy 적용 후 Ingress Gateway → 내부 서비스 통신 전부 차단
- 모든 API 요청 403 응답

### 원인
- AuthorizationPolicy에 설정한 SA 이름: `istio-ingressgateway-service-account`
- 실제 Ingress Gateway SA 이름: `istio-gateway-prod`

### 해결 과정
1. mTLS 설정 문제로 가정하고 PeerAuthentication 먼저 확인 → 이상 없음
2. AuthorizationPolicy를 하나씩 비활성화하며 범위 좁힘
3. Kiali에서 차단 구간 시각적 확인
4. SA 이름 불일치 발견 → 수정

### 파일
- gitops/prod/istio/authorization-policies.yaml

### 교훈
- 보안 정책은 전체 적용 전 단일 서비스에서 먼저 테스트
- Kiali가 원인 범위를 빠르게 좁히는 데 핵심적인 역할
- SA 이름 같은 기본값은 배포 전 체크리스트로 검증

## 5. Git 브랜치 관리 이슈

### 현상
- 로컬 브랜치와 원격 브랜치 불일치
- 잘못된 브랜치(fix/auction-cpu-request)에서 커밋 후 push rejected

### 해결
```bash
git fetch --prune          # 원격 상태 동기화
git cherry-pick <hash>     # 커밋을 main으로 이동
git branch -d <gone>       # 삭제된 원격 브랜치의 로컬 정리
```

### 커밋 규칙 (팀 규칙)
- 커밋 메시지: 한국어
- Co-Authored-By 없음
- main에 직접 push

## 6. topologySpreadConstraints DoNotSchedule → Pod 스케줄링 실패

### 현상
- 부하테스트 중 HPA가 Pod를 scale-out 하려는데 Pending 상태에서 스케줄 불가
- 일부 노드에 Pod가 몰려 있고 신규 Pod가 배치되지 않음

### 원인
- topologySpreadConstraints의 whenUnsatisfiable: `DoNotSchedule`
- AZ 간 Pod 수 불균형이 발생했을 때 스케줄러가 아예 배치를 거부

### 해결
- whenUnsatisfiable: `DoNotSchedule` → **`ScheduleAnyway`** 전체 8개 서비스 일괄 변경
- 불균형이 있더라도 일단 스케줄하고 이후 재분산

### 파일
- prod/backend/*/deployment.yaml (8개 서비스 전체)

### 교훈
- DoNotSchedule은 AZ 균형을 강제하지만 트래픽 급증 시 scale-out 자체를 막는 부작용 존재
- 가용성 우선이면 ScheduleAnyway, 균형 강제가 목적이면 DoNotSchedule

## 7. 부하테스트 중 DB Connection 폭발 → RDS Proxy 도입

### 현상
- 부하테스트 진행 중 HPA로 Pod 수가 늘어나면서 DB 연결 오류 급증
- RDS MySQL 연결 수 상한 초과

### 원인
- HikariCP 기본 설정으로 Pod 당 최대 10개 DB 연결
- Pod 수가 늘어날수록 총 연결 수 = Pod 수 × 10 → RDS 연결 한도 초과

### 해결
- DB_HOST를 RDS 직접 접속 → **RDS Proxy** 엔드포인트로 전환
- RDS Proxy가 연결 풀링 담당, 실제 RDS로의 연결 수를 일정하게 유지
```
변경 전: t1-prod-rds.c3cqs4gaouah.ap-northeast-2.rds.amazonaws.com
변경 후: t1-prod-rds-proxy.proxy-c3cqs4gaouah.ap-northeast-2.rds.amazonaws.com
```

### 파일
- prod/backend/common/configmap-common.yaml

### 교훈
- MSA + HPA 환경에서는 Pod 수 × 연결 수가 RDS 한도를 초과할 수 있음
- RDS Proxy는 인프라 레벨에서 connection explosion을 방어하는 표준 패턴

## 8. HPA 진동 — auction CPU request 저설정

### 현상
- auction 서비스 HPA가 수렴하지 않고 Pod 수가 계속 오르내림 (oscillation)
- CPU 사용률이 HPA 목표치(60%)를 지속적으로 초과

### 원인
- CPU request가 100m로 너무 낮게 설정
- 실제 앱 idle CPU가 이미 100m에 근접 → HPA가 상시 scale-out 판단
- HPA는 `실제 사용량 / request`로 계산하므로 request가 낮으면 비율이 과대 측정됨

### 해결
- CPU request: 100m → **200m**, limit: 300m → **500m**

### 파일
- prod/backend/auction/deployment.yaml

### 교훈
- HPA CPU 기반 오토스케일링 시 request 값이 기준선 역할
- request를 실제 idle 사용량보다 충분히 높게 설정해야 HPA가 안정적으로 수렴

## 9. queue-worker ConfigMap 누락 → Spring Security 자동 설정 충돌

### 현상
- queue-worker Pod 기동 후 보안 관련 오류로 정상 동작하지 않음
- queue-worker는 HTTP 엔드포인트 없이 메시지 소비만 하는데 Spring Security가 자동 적용됨

### 원인
- Spring Boot autoconfigure가 Security 설정을 자동 활성화
- queue-worker는 웹 서버가 없어서 Security 자동 설정이 불필요하나 충돌 발생
- 필요한 ConfigMap이 누락된 상태로 배포됨

### 해결
- queue-worker 전용 ConfigMap 추가
```yaml
data:
  SPRING_AUTOCONFIGURE_EXCLUDE: >-
    org.springframework.boot.autoconfigure.security.servlet.SecurityAutoConfiguration,
    org.springframework.boot.actuate.autoconfigure.security.servlet.ManagementWebSecurityAutoConfiguration
```

### 파일
- prod/backend/queue-worker/queue-worker-config.yaml

## 11. SSE 경매 스트림 연결 끊김 (Envoy timeout)

### 현상
- 경매 실시간 스트림(`/auctions/*/stream`) 연결이 일정 시간 후 강제 종료
- 클라이언트가 SSE 연결을 맺었다가 끊기는 현상 반복

### 원인
두 곳에서 timeout이 발생
1. **Istio Envoy**: VirtualService 기본 timeout(10s)이 장기 연결 SSE를 강제 종료
2. **ALB**: idle timeout 기본값 60초 초과 시 연결 끊음

### 해결
- VirtualService에 SSE 전용 route 추가
```yaml
- match:
    - uri:
        regex: /auctions/[^/]+/stream
  timeout: 0s          # timeout 해제 (SSE는 장기 연결)
  retries:
    attempts: 0        # 재시도 금지 (연결 중복 방지)
  headers:
    response:
      set:
        X-Accel-Buffering: "no"   # Envoy 응답 버퍼링 비활성화
```
- ALB idle timeout: 60s → **3600s**
```yaml
alb.ingress.kubernetes.io/load-balancer-attributes: idle_timeout.timeout_seconds=3600
```

### 파일
- prod/istio/traffic-management/virtual-services.yaml
- prod/ingress.yaml

### 교훈
- SSE/WebSocket 같은 장기 연결은 Istio + ALB 양쪽 timeout 모두 설정 필요
- Envoy는 응답 버퍼링도 비활성화해야 실시간 스트림이 정상 동작

## 12. Prometheus 메트릭 수집 안 됨 (PodMonitor → additionalScrapeConfigs)

### 현상
- Grafana 대시보드에 백엔드 서비스 메트릭이 수집되지 않음
- PodMonitor 리소스를 생성했지만 Prometheus가 파드를 scrape하지 않음

### 원인
- kube-prometheus-stack의 PodMonitor selector 설정과 popcon-prod 네임스페이스 간 매칭 문제
- Istio 사이드카 환경에서 PodMonitor CRD가 예상대로 동작하지 않음

### 해결
- PodMonitor 방식 포기, `additionalScrapeConfigs` 방식으로 전환
- `prometheus.io/scrape: "true"` 어노테이션 기반 자동 discovery
```yaml
additionalScrapeConfigs:
  - job_name: popcon-backend-metrics
    kubernetes_sd_configs:
      - role: pod
        namespaces:
          names: [popcon-prod]
    relabel_configs:
      - source_labels: [__meta_kubernetes_pod_annotation_prometheus_io_scrape]
        action: keep
        regex: "true"
      - source_labels: [__meta_kubernetes_pod_label_app_kubernetes_io_part_of]
        action: keep
        regex: popcon
```

### 파일
- prod/monitoring/helm-values/values-prometheus.yaml

### 교훈
- Istio 사이드카 환경에서 PodMonitor는 네임스페이스 selector 설정이 까다로움
- additionalScrapeConfigs + 어노테이션 방식이 더 직관적이고 유연

## 13. JVM 타임존 UTC 문제

### 현상
- 로그 타임스탬프, DB 저장 시간이 모두 UTC 기준으로 찍힘

- prod/backend/common/configmap-common.yaml

### 교훈

- 공통 ConfigMap으로 전체 서비스에 일괄 적용하면 누락 방지

## 14. Kiali signing_key 길이 오류 + ArgoCD OutOfSync 반복

### 현상 1 (signing_key 길이)
- Kiali 로그인 시 인증 오류 발생
- Kiali Pod 로그에 signing_key 관련 오류

### 원인
- Kiali JWT signing_key는 정확히 **32바이트** 요구
- `"popcon-kiali-signing-key-2026"` → 31바이트로 1바이트 부족

### 해결
- `"popcon-kiali-signing-key-2026abc"` (32바이트)로 수정

### 현상 2 (ArgoCD OutOfSync)
- ArgoCD가 Kiali를 계속 OutOfSync로 표시하며 반복 배포
- 배포할 때마다 signing_key가 랜덤 생성되어 drift 발생

### 해결
- signing_key를 values 파일에 고정값으로 명시 → ArgoCD가 더 이상 drift 감지하지 않음

### 파일
- prod/istio/helm-values/values-kiali.yaml

### 교훈
- Helm chart의 랜덤 생성 필드는 ArgoCD GitOps와 충돌 → 반드시 고정값 명시
- 외부 툴의 설정 요구사항(바이트 길이 등)은 공식 문서에서 정확히 확인 필요

## 공통 교훈
1. **로그를 먼저** — 증상만 보면 원인을 잘못 짚기 쉬움. 타임스탬프와 에러 메시지가 핵심
2. **반복되는 문제는 표준화로** — startupProbe처럼 같은 문제가 서비스마다 반복되면 공통 설정 검토
3. **시각화 도구 적극 활용** — Kiali가 Istio 문제 범위 좁히는 데 결정적
4. **근본 원인 vs 증상** — 좀비 노드 수동 삭제는 증상 치료, Spot 풀 고갈 해결이 근본 치료
5. **HPA 기준선 설계** — CPU request는 HPA 계산의 분모. idle 사용량보다 충분히 높아야 진동 방지
6. **MSA scale-out과 DB 연결** — Pod 수 증가 = DB 연결 수 증가. RDS Proxy로 선제 대응 필요
7. **설정 누락은 배포 전 체크리스트로** — 환경변수/ConfigMap 누락은 앱 배포 후에야 드러남
8. **장기 연결(SSE/WebSocket)** — Istio + ALB 양쪽 timeout 모두 명시. Envoy 버퍼링도 비활성화
9. **GitOps + Helm 랜덤 필드** — 랜덤 생성되는 Helm 값은 GitOps와 충돌. 고정값으로 명시 필요
