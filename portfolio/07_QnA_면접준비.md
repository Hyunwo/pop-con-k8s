# 07. QnA 및 면접 준비

## 아키텍처

**Q. 요청 흐름을 간단히 설명해주세요.**
> 사용자 요청이 Cloudflare → ALB → Istio Ingress Gateway → EKS 각 서비스 순서로 전달됩니다.
> 각 단계에서 엣지 방어, 로드 분산, 서비스 진입 제어를 단계적으로 거치도록 설계했습니다.

**Q. Cloudflare 없이 ALB만 써도 되지 않나요?**
> ALB는 로드 분산이 주목적이고 DDoS 방어나 CDN 캐싱은 제공하지 않습니다.
> Cloudflare를 앞단에 두면 애플리케이션에 도달하기 전에 비정상 트래픽을 걸러낼 수 있습니다.

**Q. 단일 장애점은 없나요?**
> RDS는 Multi-AZ로 가용성을 확보했고, 각 서비스는 2개 이상의 Pod를 다른 노드에 분산 배치했습니다.
> Cloudflare도 글로벌 분산 네트워크라 단일 장애점이 아닙니다.
> 다만 Redis는 단일 노드로 운영 중이어서 향후 개선이 필요한 지점입니다.

## Karpenter

**Q. Cluster Autoscaler 대신 Karpenter를 선택한 이유는?**
> CA가 노드 그룹 단위로 수 분이 걸리는 반면, Karpenter는 Pending 상태인 Pod를 감지해
> 필요한 노드를 직접 프로비저닝하기 때문에 수 초 단위로 빠르게 확장이 가능합니다.
> 팝업 오픈처럼 수요가 짧은 시간에 몰리는 서비스에 더 적합하다고 판단했습니다.

**Q. Spot 인스턴스 쓰다가 중단되면 어떻게 되나요?**
> AWS가 Spot 중단 신호를 2분 전에 보내고, Karpenter가 SQS를 통해 이를 감지해서
> 해당 노드의 Pod를 다른 노드로 미리 이동시킵니다.
> On-demand 인스턴스를 함께 설정해서 Spot 가용성이 부족할 때 대체되도록 했습니다.

**Q. 스케일인은 어떻게 동작하나요?**
> Karpenter의 Consolidation 정책으로 사용률이 낮은 노드의 Pod를 다른 노드로 합치고 빈 노드를 자동 삭제합니다.
> 저희는 5분 유휴 후 통합을 시도하도록 설정했습니다.

## Istio

**Q. Istio 쓰는 이유가 뭔가요? nginx ingress랑 뭐가 다른가요?**
> nginx ingress는 외부 트래픽 진입만 담당합니다.
> Istio는 클러스터 내부 서비스 간 통신까지 제어할 수 있습니다.
> 저희는 내부 서비스 간 mTLS 암호화, Circuit Breaker, 트래픽 정책을 적용하기 위해 Istio를 선택했습니다.

**Q. Istio 넣으면 리소스 오버헤드가 있지 않나요?**
> 맞습니다. 각 Pod에 Envoy 사이드카가 붙기 때문에 추가 리소스가 소비됩니다.
> 저희는 사이드카 CPU를 10m, 메모리를 64Mi로 제한해서 오버헤드를 최소화했습니다.

**Q. mTLS가 뭔가요?**
> 일반 TLS는 클라이언트가 서버를 검증하지만, mTLS는 서버도 클라이언트를 검증합니다.
> 저희는 STRICT 모드로 설정해서 Istio 사이드카가 없는 서비스는 내부 통신 자체가 불가능하도록 막았습니다.

**Q. Circuit Breaker는 왜 적용했나요?**
> 하나의 서비스가 느려지거나 죽었을 때 연쇄 장애가 전파되는 것을 막기 위해서입니다.
> 연속 실패가 일정 횟수를 넘으면 해당 Pod를 일시적으로 격리하고, 일정 시간 후 자동 복구됩니다.

**Q. VirtualService랑 Kubernetes Service랑 뭐가 다른가요?**
> Kubernetes Service는 Pod를 묶어서 접근 가능하게 해주는 네트워크 엔드포인트입니다.
> VirtualService는 그 위에서 어느 Service로 보낼지 Istio가 제어하는 라우팅 규칙입니다.
> Kubernetes Service가 목적지라면, VirtualService는 목적지까지 가는 규칙입니다.

**Q. DestinationRule은 뭔가요?**
> VirtualService가 "어디로 보낼지"를 정의한다면,
> DestinationRule은 "그 목적지에 어떻게 연결할지"를 정의합니다.
> 저희는 여기에 Circuit Breaker와 Connection Pool 설정을 적용했습니다.

**Q. Istio 도입 전후 성능 비교해봤나요?**
> 도입 전후 비교 측정은 하지 못했습니다.
> 다만 사이드카 CPU 10m, 메모리 64Mi로 제한해서 오버헤드를 최소화했고,
> 부하테스트에서 정상 동작을 확인했습니다.

## HPA / KEDA

**Q. HPA는 어떤 기준으로 스케일아웃 하나요?**
> CPU 사용률 60%를 목표로 설정했습니다.
> Pod 1개가 CPU request 200m 기준일 때 실제 사용량이 120m을 넘으면 스케일아웃이 트리거됩니다.

**Q. 왜 60%로 설정했나요?**
> 100%로 설정하면 이미 CPU가 가득 찬 상태에서 스케일아웃이 시작되기 때문에
> 새 Pod가 뜨기 전까지 응답 지연이 발생합니다.
> 60%는 여유를 두고 미리 확장해서 트래픽 급증에 선제적으로 대응하기 위한 수치입니다.

**Q. KEDA는 왜 사용하지 않았나요?**
> CPU 기반 HPA로 먼저 구성하고 부하테스트로 한계를 확인하는 것을 우선순위로 잡았습니다.
> 부하테스트 결과 Queue가 공통 병목으로 확인됐기 때문에,
> 향후 Queue 길이 기반으로 Queue Worker를 스케일링하는 방향으로 KEDA 도입을 검토할 수 있습니다.

**Q. KEDA를 썼으면 Queue 병목이 해결됐을까요?**
> Queue 병목의 원인이 처리 속도인지, 연결 수인지에 따라 다릅니다.
> KEDA만 도입한다고 해결되는 문제는 아니고, RDS Proxy와 함께 전체 파이프라인을 함께 확장해야 합니다.

## 데이터 계층

**Q. RDS Proxy는 왜 쓰셨나요?**
> Pod 수가 늘어나면 DB 연결 수도 함께 폭발적으로 증가합니다.
> RDS Proxy가 연결을 풀링해서 실제 DB에는 일정 수의 연결만 유지되도록 합니다.

**Q. Redis 장애 나면 어떻게 되나요?**
> Redis는 캐시와 실시간 상태 처리 용도로 사용했습니다.
> 장애 시 캐시 히트율이 떨어져 DB 부하가 급증할 수 있고, 대기열 상태도 유실될 수 있습니다.
> 현재 단일 노드라 향후 Redis Cluster나 Sentinel 구성이 필요한 지점입니다.

**Q. Parameter Store 말고 Secrets Manager는 왜 안 쓰셨나요?**
> Parameter Store는 무료 티어에서 충분한 기능을 제공하고,
> External Secrets와의 연동도 잘 지원합니다.
> 비용 대비 요구사항을 충족할 수 있어서 선택했습니다.

## MSA

**Q. 서비스를 어떤 기준으로 나눴나요?**
> 트래픽 패턴과 확장 단위를 기준으로 나눴습니다.
> 대기열은 이벤트 오픈 순간에만 트래픽이 집중되고, 인증은 상시 일정한 트래픽이 발생합니다.
> 패턴이 다른 서비스를 묶으면 독립적인 스케일링이 불가능하기 때문에 분리했습니다.

**Q. 각 서비스마다 DB가 따로 있나요?**
> 현재는 하나의 RDS MySQL에 서비스별로 데이터베이스를 분리해서 사용하고 있습니다.
> 물리적으로 RDS 인스턴스를 나누지는 않았고, 완전한 DB 분리는 향후 개선 방향입니다.

**Q. 서비스가 많으면 배포가 복잡하지 않나요?**
> ArgoCD로 GitOps 방식으로 관리합니다.
> gitops 레포에 서비스별 매니페스트를 관리하고, 변경사항을 push하면 ArgoCD가 자동으로 반영합니다.
> ArgoCD 대시보드에서 전체 서비스 동기화 상태를 한눈에 확인할 수 있습니다.

## 부하테스트

**Q. 목표 CCU 22,500명인데 실제로 5,000 VU밖에 못 넣었잖아요. 검증이 됐다고 할 수 있나요?**
> 설계 목표는 22,500 VU였으나 테스트 환경 한계로 최대 5,000 VU까지만 투입했습니다.
> 이 구간에서 확인한 지표를 바탕으로 병목 지점을 파악했고,
> 어떤 구간을 개선해야 목표 CCU에 도달할 수 있는지 방향을 도출했습니다.

**Q. Queue가 공통 병목이라고 하셨는데, 어떻게 개선할 건가요?**
> 단기적으로는 Queue Worker Pod 수를 늘려 처리량을 확보할 수 있습니다.
> 장기적으로는 KEDA로 Queue 길이 기반 스케일링을 도입하고,
> Redis 클러스터 구성으로 처리 용량을 확장하는 방향을 검토하고 있습니다.

**Q. 초과 판매는 어떻게 방지했나요?**
> Redis의 원자적 연산으로 재고를 관리했습니다.
> 동시에 여러 요청이 들어와도 Redis가 순서를 보장하기 때문에
> 재고보다 많은 낙찰이 발생하지 않습니다.
> 부하테스트에서 초과 판매 0건으로 검증했습니다.

## 재해 복구

**Q. 재해 복구 전략은 어떻게 되나요?**
> RDS Multi-AZ 기준으로 페일오버는 통상 1~2분 이내입니다.
> RDS Proxy가 연결을 유지해줘서 애플리케이션 레벨 중단을 최소화합니다.
> RDS 자동 백업으로 Point-in-Time Recovery도 가능합니다.
> 다만 멀티 리전 DR은 구성하지 않았고, 이 부분은 향후 개선이 필요한 지점입니다.

**Q. Kafka는 왜 사용하지 않았나요?**
> Kafka는 대용량 메시지를 안정적으로 처리하는 데 강점이 있지만 운영 복잡도가 높습니다.
> 저희 서비스에서 비동기 처리가 필요한 구간은 대기열 워커 정도였고,
> 이 정도 규모에서는 Redis 기반 큐로 충분히 처리 가능하다고 판단했습니다.
> 서비스가 더 커지고 메시지 재처리나 이벤트 소싱이 필요해진다면 Kafka 도입을 검토할 수 있습니다.

## IRSA

**Q. AWS 자격증명은 어떻게 관리했나요?**
> Access Key를 코드나 환경변수에 넣지 않고 IRSA(IAM Roles for Service Accounts)를 사용했습니다.
> ServiceAccount에 IAM Role ARN을 어노테이션으로 달면, EKS가 OIDC 토큰을 자동으로 마운트해서
> AWS STS로부터 임시 자격증명을 발급받아 AWS 리소스에 접근합니다.

**Q. IRSA를 어떤 서비스에 적용했나요?**
> ALB Controller, External Secrets, EBS CSI Driver, Loki, 그리고 backend-user 서비스에 적용했습니다.
> backend-user는 사용자 프로필 이미지를 S3에 업로드/삭제하기 위해 S3 권한이 필요했고,
> assets-popcon-store 버킷의 profiles/* 경로에만 접근 가능하도록 최소 권한 원칙을 적용했습니다.

**Q. IRSA가 왜 Access Key보다 안전한가요?**
> Access Key는 유출되면 영구적으로 사용 가능하지만,
> IRSA는 STS에서 발급하는 임시 자격증명을 사용해서 자동 만료됩니다.
> 또한 특정 네임스페이스의 특정 ServiceAccount만 해당 Role을 Assume할 수 있어서
> 권한 범위가 명확하게 제한됩니다.
